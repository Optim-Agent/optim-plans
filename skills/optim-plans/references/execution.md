# Execution Contract

Execution has a mandatory immutable execution manifest and a single-use human approval gate. The approval question shows the finalized plan hash, base commit, manifest hash, stable item DAG/order, adapter argv/config, path allowlists, run branch, worktree path, local integration destination, sandbox/network policy, verification commands, verification timeouts, and retry limits. Do not offer `Auto-complete` on the execution approval question. A prior human `Jump to executor` / `skip-refinement-execute` answer directly approves that gate after the manifest is recorded; no other refinement answer does.

Use only the controller commands: `prepare-execution --repo --manifest <path>`, `start-execution --repo --approval-nonce <nonce>`, `run-item --repo --item-id <id>`, `retry-item --repo --item-id <id> --approval-nonce <nonce>`, and `finish-run --repo --outcome <integrated|pr-opened|kept|discarded|failed|aborted> --approval-nonce <nonce>`. Execution may start only after the manifest hash still matches, the approval nonce was answered with approve and not consumed, and the source worktree is clean at the approved committed base.

Workers launch only through a Claude or Codex adapter argv array with `shell=False`, an explicit environment, and the one controller-owned run worktree and run branch as cwd. Default executor manifests use the same-platform delegated worker (`codex` host -> Codex sub-agent, `claude` host -> Claude sub-agent), falling back to Codex only when the host is unknown. Do not launch cross-platform delegated workers: Codex must not call Claude, and Claude must not call Codex. Codex worker argv must not request a structured-output schema; the controller reads the required nonce/item/status/evidence JSON envelope from worker stdout. When delegated execution uses Claude, the worker argv must select the `optim-plans-executor` subagent with `--agent` as a foreground standalone agent, not `--bg` and not a hidden background subagent. The controller runs items in serial topological order. Each item starts from the latest verified checkpoint commit; dependents do not start until every dependency has a checkpoint.

Worker exit records `worker_completed` only. The controller runs the verification argv, then audits tracked, staged, untracked, ignored, symlink, gitlink/submodule, nested-repository, and out-of-scope deltas. It also checks protected Git metadata: source HEAD/ref, refs except the run branch, config, hooks, and registered worktrees. Only passing controller verification plus path and protected Git metadata audits records `item_verified` and creates the checkpoint commit. Drift is preserved as evidence and is not auto-restored.

Path allowlists are integration allowlists, not host confinement. The trust boundary is repository-integrity detection and integration gating for a trusted local repo/process; it is not host confinement, and it does not prevent a trusted worker from writing outside the worktree or touching shared metadata before detection. Hooks and agent sandboxes are defense in depth.

Failures enter `awaiting_retry_decision` with bounded evidence and without a checkpoint. A retry requires explicit retry approval. Auto-complete cannot approve finish-wrap integration, cleanup, merge, push, PR, keep, discard, retry restoration, waivers, or `not_achievable`; delegated agents cannot approve them either.

After every item is verified and the final audits pass, the run enters `awaiting_integration`; execution is not complete yet. Finish wrap must record one evidence-backed outcome: `integrated` proves the manifest-bound local destination contains the final checkpoint, `pr-opened` proves the PR URL and fetched remote ref contain it, `kept` preserves the run worktree and branch, and `discarded` requires explicit confirmation and removes only validated controller-owned state. `Failed` or `aborted` records failure or abort evidence in the terminal event and preserves the worktree unless confirmed discard is requested.
