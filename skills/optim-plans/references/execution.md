# Execution Contract

Execution has a mandatory immutable execution manifest and a single-use human approval gate. The execution runtime is an executing-validating (ameliorating) ring: executor output goes to a read-only validator before controller verification, and only a valid validator `fail` after safe-audit approval can feed bounded feedback into another executor attempt. CLI adapter worker manifests must include a smoke argv that starts with the worker adapter argv, and `prepare-execution` records the immutable manifest only after that smoke command returns a JSON object with `"status":"valid"`. Successful smoke tests are stored as exact cached smoke-tested worker block entries in Git-common `config.json` under `smoke_tested_workers`; only an exact block match can skip a later smoke launch. Codex host executor manifests may instead use `host-multi-agent` mode, which has no smoke argv and binds the canonical host launch block: platform, mode, agent type, model, reasoning effort, service tier when present, prompt protocol, prompt hash, allowed tools, sandbox, and result schema. New `0.1.2` manifests must explicitly set `schema_version`, `protocol_version`, `validator_worker`, `validator_prompt`, `validator_retry_limit`, and per-item `validator.check_ids`. The validator prompt must say to aim for the best complete implementation, consider the problem from multiple angles, and avoid accepting an MVP-only task completion. The approval question shows the finalized plan hash, base commit, manifest hash, stable item DAG/order, host launch block or adapter argv/config plus smoke, validator config/prompt/check IDs, path allowlists, run branch, worktree path, local integration destination, sandbox/network policy, verification commands, verification timeouts, and retry limits. Do not offer `Auto-complete` on the execution approval question. A prior human `Jump to executor` / `skip-refinement-execute` answer directly approves that gate after the manifest is recorded; no other refinement answer does.

Use only the controller commands. Shared setup is `prepare-execution --repo --manifest <path>` and `start-execution --repo --approval-nonce <nonce>`. CLI fallback uses `run-item --repo --item-id <id>`; for current Claude executors, `run-item` starts the `optim-plans-executor` with `--agent` as a foreground standalone subagent, waits synchronously for the adapter process, and reads the stdout JSON envelope. Host-multi-agent single-item execution uses `assign-item --repo --item-id <id>`; when the response includes `resume_action`, run `authorize-resume --repo --item-id <id> --assignment-nonce <nonce> --prior-agent-handle <handle> --launch-block <json>` for session resume, host `resume_agent` if needed, host `send_input` with the launch block, then `register-agent --resume-nonce <nonce> --agent-handle <same-handle>` and host `wait_agent`. If resume/send fails before registration, run `fail-item --resume-nonce <nonce> --resume-failure-kind <resume|send_input|resume_or_send> --evidence <summary>`. If no resume action exists or resume is unavailable, use `authorize-spawn`, host `spawn_agent`, `register-agent --launch-nonce <nonce>`, host `wait_agent`, `complete-item` or `fail-item`, then `advance-item --repo --item-id <id>`. Host single-item validation follows the same order with `authorize-validator-resume` / `register-validator --resume-nonce` before `authorize-validator-spawn` / `register-validator --launch-nonce`, then `complete-validator` or `fail-validator`. Host batch execution uses `assign-batch --repo <repo>` over the next continuous ready manifest prefix; when offered, run `authorize-batch-resume` / `register-batch-agent --resume-nonce` before `authorize-batch-spawn` / `register-batch-agent --launch-nonce`, then `complete-batch` or `fail-batch` and `advance-batch --batch-id <id>`. If `advance-batch` returns a host validator launch block, use `authorize-batch-validator-resume` / `register-batch-validator --resume-nonce` before `authorize-batch-validator-spawn` / `register-batch-validator --launch-nonce`, then `complete-batch-validator --result <json>` or `fail-batch-validator --reason interrupted|process|crash|timeout|unknown`. Single-item recovery uses `retry-item --repo --item-id <id> [--approval-nonce <nonce>]`; batch recovery uses `retry-batch --repo --batch-id <id> [--approval-nonce <nonce>]`; manual finish recovery uses `finish-run --repo --outcome <integrated|pr-opened|kept|discarded|failed|aborted> --approval-nonce <nonce>`. Execution may start only after the manifest hash still matches, the approval nonce was answered with approve and not consumed, and the source worktree is clean at the approved committed base.

Before building the execution manifest, ask `agent-choice --role executor`; default only from `executor_worker.choice`. Immediately after the executor choice, ask `agent-choice --role validator`; default only from `validator_worker.choice` and recommend background delegation. If the executor choice is `background`, continue to executor model/effort and `worker-config`; do the same for the validator. If executor execution is `foreground`, build a foreground executor worker block with the controller executor prompt hash and run it in the current session through `run-item` or `assign-item`, which returns the manifest-bound assignment and launch block instead of spawning a worker; after the current session completes the item, use `complete-item` and `advance-item`. Default Codex executor and validator manifests use the same-platform delegated worker (`codex` host -> Codex sub-agent) through host `spawn_agent` / `wait_agent`; current Claude executor manifests use the same-platform CLI adapter (`claude` host -> Claude sub-agent) through `run-item` synchronous wait/stdout until a host tool path exists. The legacy `background` choice does not mean current Claude host/background execution. Validator workers are read-only. Do not launch cross-platform delegated workers: Codex must not call Claude, and Claude must not call Codex.

For host-multi-agent execution, `assign-item` persists an assignment nonce atomically with `item_started` and returns the exact launch block. `assign-batch` persists one assignment nonce atomically with `batch_started`; the selected `item_ids` are a continuous ready prefix from canonical manifest order, target 3-6 with tail, dependency, and high-risk exceptions. Batch events (`batch_started`, `batch_completed`, `batch_validator_assigned`, `batch_validator_result_recorded`, `batch_checkpoint_created`, `batch_retry_restored`) are authoritative, and status/summary project per-item state from them. Item commands reject members of an active batch attempt. `authorize-resume`, `authorize-batch-resume`, `authorize-validator-resume`, and `authorize-batch-validator-resume` validate the launch block and return a single-use `resume_nonce` bound to the target assignment or validator nonce, exact prior handle, exact launch block hash, worker or validator config hash, and validator prompt hash/prompt hash where applicable. Resumed registration must use the same prior handle; that registered handle then enters the existing `*_agent_registered` wait/completion path. `authorize-spawn` / `authorize-batch-spawn` validate launch blocks against the approved manifest before any write-capable host spawn and return a single-use launch nonce. Launch blocks include prior agent handles only when a related executor or validator session can be reused and has not had a later same-role/config/prompt resume/send/worker failure; they also include bounded `prior_context` and `ignored_audit_noise` telling workers to leave default audit noise plus manifest `ignored_runtime_outputs` alone. The controller automatically adds the active `docs/optim-plans/...` artifact dir to new execution manifests. `ignored_runtime_outputs` entries are repo-relative path scopes for new runtime output files or directories only; they may hide untracked or ignored `??` / `!!` status entries from audit and fingerprint checks, but never tracked, staged, symlink, gitlink, nested-repo, or protected metadata changes. Resume/send failures use only the existing `worker_failed`, `batch_worker_failed`, `validator_failed`, or `batch_validator_failed` event types with prior handle, target nonce, resume nonce, failure kind, and bounded evidence. `advance-item` and `advance-batch` are replayable: they report assigned, resume-authorized, spawn-authorized, registered, completed, failed, checkpointed, or finalized phase and safely resume validation, verification, checkpointing, final audit, or failure recording without duplicate spawning.

CLI adapter workers launch only through a Claude or Codex adapter argv array with `shell=False`, an explicit environment, and the one controller-owned run worktree and run branch as cwd. Codex worker argv must not request a structured-output schema; the controller reads the required nonce/item/status/evidence JSON envelope from worker stdout. When delegated execution uses Claude CLI, the worker argv must select the `optim-plans-executor` subagent with `--agent` as a foreground standalone agent, not Codex-style `wait_agent`, not `--bg`, not a hidden background subagent, not host/background mode, and not background notification/outputFile wait. The controller runs items in serial topological order. Each item starts from the latest verified checkpoint commit; dependents do not start until every dependency has a checkpoint.

Worker exit records `worker_completed` or `batch_completed` only. For `0.1.2` manifests, the controller runs the validator before verification. Valid single-item validator result JSON must include `status`, `evidence`, `feedback_for_executor`, and `checked_items`, plus run ID, item ID, attempt, nonce, validator config hash, validator prompt hash, and delta fingerprint. Valid batch validator result JSON must additionally bind `batch_id`, ordered `item_ids`, the batch assignment nonce, and aggregate `checked_items` equal to every check ID covered by the batch. Valid pass/fail results record `validator_result_recorded` or `batch_validator_result_recorded`; malformed, stale, wrong, partial, or mismatched results record protocol rejection. The controller compares the delta fingerprint before validator assignment, at result receipt, before verification, and after verification; mismatch enters manual recovery and never checkpoints. Retryable ordinary failures (`worker_failed`, `verification_failed`, validator `fail`, and batch equivalents) auto-restore after a safe audit and continue the executing-validating loop. The controller records bounded evidence/feedback, restores to the item or batch base, and injects retry feedback into the next executor launch block or CLI env/state as the amelioration input. Three consecutive equivalent retryable failures or five retryable failures since the latest checkpoint/base record `execution_blocked` or `batch_execution_blocked`; `validator_retry_limit` is compatibility/display metadata and must not stop ordinary validator-fail retry before this blocked detector. Unsafe audit failures, protocol failures, drift, and integration failures preserve evidence and enter manual recovery instead of looping. After validator pass, the controller runs the verification argv, then audits tracked, staged, untracked, ignored, symlink, gitlink/submodule, nested-repository, and out-of-scope deltas; default ignored audit noise is tolerated for `.xsw/`, `.pytest_cache/`, `__pycache__/`, and `*.pyc`, and the active artifact dir plus manifest `ignored_runtime_outputs` may additionally tolerate new untracked/ignored runtime output scopes. It also checks protected Git metadata: source HEAD/ref, refs except the run branch, config, hooks, and registered worktrees. Single-item success records `item_verified` and creates one checkpoint commit; batch success records one all-or-nothing `batch_checkpoint_created` commit and does not leave partial verified state on failure. Drift is preserved as evidence and is not auto-restored.

Path allowlists are integration allowlists, not host confinement. The trust boundary is repository-integrity detection and integration gating for a trusted local repo/process; it is not host confinement, and it does not prevent a trusted worker from writing outside the worktree or touching shared metadata before detection. Hooks and agent sandboxes are defense in depth.

Manual recovery failures enter `awaiting_retry_decision` with bounded evidence and without a checkpoint. Ordinary retryable failures do not pause there; they auto-restore and continue until success or `blocked`. `request_retry`, `request_batch_retry`, and `request_finish_approval` are manual recovery commands for non-retryable or blocked recovery. Status exposes a direct `retry-item` / `retry-batch` resume command for retryable failures, manual recovery details for non-retryable failures, and blocked item/batch details for blocked retry loops. Auto-complete cannot approve finish-wrap integration, cleanup, merge, push, PR, keep, discard, retry restoration for manual recovery, waivers, or `not_achievable`; delegated agents cannot approve them either.

After every item is verified and the final audits pass, execution automatically fast-forwards the clean checked-out manifest destination branch to the final checkpoint, runs the full local proof, records `run_finished` with outcome `integrated`, preserves the run worktree and branch, and releases only the matching active pointer. If a precondition or fast-forward check fails before destination mutation, record `awaiting_integration` with bounded evidence and leave the destination unchanged. If full proof fails after fast-forward, record `integration_verification_failed` with stage plus before/after destination OIDs and keep lifecycle `awaiting_integration`; status must create or surface a finish approval with `integrated`, `pr-opened`, `kept`, `discarded`, `failed`, and `aborted`. Manual finish recovery can still record one evidence-backed outcome: `integrated` proves the manifest-bound local destination contains the final checkpoint, requires the checked-out destination worktree to match that object, then runs the full local proof before `run_finished`; proof failure records `integration_verification_failed` and stays in integration recovery, `pr-opened` proves the PR URL and fetched remote ref contain it, `kept` preserves the run worktree and branch, and `discarded` requires explicit confirmation and removes only validated controller-owned state. `Failed` or `aborted` records failure or abort evidence in the terminal event and preserves the worktree unless confirmed discard is requested.
