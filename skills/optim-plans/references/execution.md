# Execution Contract

Execution has a mandatory immutable execution manifest and a single-use human approval gate. CLI adapter worker manifests must include a smoke argv that starts with the worker adapter argv, and `prepare-execution` records the immutable manifest only after that smoke command returns a JSON object with `"status":"valid"`. Successful smoke tests are stored as exact cached smoke-tested worker block entries in Git-common `config.json` under `smoke_tested_workers`; only an exact block match can skip a later smoke launch. Codex host executor manifests may instead use `host-multi-agent` mode, which has no smoke argv and binds the canonical host launch block: platform, mode, agent type, model, reasoning effort, service tier when present, prompt protocol, prompt hash, allowed tools, sandbox, and result schema. The approval question shows the finalized plan hash, base commit, manifest hash, stable item DAG/order, host launch block or adapter argv/config plus smoke, path allowlists, run branch, worktree path, local integration destination, sandbox/network policy, verification commands, verification timeouts, and retry limits. Do not offer `Auto-complete` on the execution approval question. A prior human `Jump to executor` / `skip-refinement-execute` answer directly approves that gate after the manifest is recorded; no other refinement answer does.

Use only the controller commands. Shared setup is `prepare-execution --repo --manifest <path>` and `start-execution --repo --approval-nonce <nonce>`. CLI fallback uses `run-item --repo --item-id <id>`. Host-multi-agent execution uses `assign-item --repo --item-id <id>`, `authorize-spawn --repo --item-id <id> --assignment-nonce <nonce> --launch-block <json>`, host `spawn_agent`, `register-agent --repo --item-id <id> --assignment-nonce <nonce> --launch-nonce <nonce> --agent-handle <handle> --launch-block <json>`, host `wait_agent`, `complete-item` or `fail-item`, then `advance-item --repo --item-id <id>`. Recovery uses `retry-item --repo --item-id <id> [--approval-nonce <nonce>]`, and manual finish recovery uses `finish-run --repo --outcome <integrated|pr-opened|kept|discarded|failed|aborted> --approval-nonce <nonce>`. Execution may start only after the manifest hash still matches, the approval nonce was answered with approve and not consumed, and the source worktree is clean at the approved committed base.

Before building the execution manifest, ask `agent-choice --role executor`; default only from `executor_worker.choice`. If the executor choice is `background`, continue to executor model/effort and `worker-config`. If it is `foreground`, stop because foreground executor execution is unsupported until it has a safe manifest-bound flow. Default Codex executor manifests use the same-platform delegated worker (`codex` host -> Codex sub-agent) through host `spawn_agent` / `wait_agent`; Claude executor manifests use the same-platform CLI adapter (`claude` host -> Claude sub-agent) until a host tool path exists. Do not launch cross-platform delegated workers: Codex must not call Claude, and Claude must not call Codex.

For host-multi-agent execution, `assign-item` persists an assignment nonce atomically with `item_started` and returns the exact launch block. `authorize-spawn` validates that block against the approved manifest before any write-capable host spawn and returns a single-use launch nonce. The host then calls `spawn_agent` with that approved block, records the returned handle through `register-agent`, waits with `wait_agent`, records `complete-item` or `fail-item` with the assignment nonce and registered handle, and calls `advance-item`. If the host is interrupted after authorization but before registration, it may register the known handle with the unused launch nonce, or fail the item with the assignment nonce plus unused launch nonce if the handle was lost. `advance-item` is replayable: it reports assigned, spawn-authorized, registered, completed, failed, checkpointed, or finalized phase and safely resumes verification, checkpointing, final audit, or failure recording without duplicate spawning.

CLI adapter workers launch only through a Claude or Codex adapter argv array with `shell=False`, an explicit environment, and the one controller-owned run worktree and run branch as cwd. Codex worker argv must not request a structured-output schema; the controller reads the required nonce/item/status/evidence JSON envelope from worker stdout. When delegated execution uses Claude CLI, the worker argv must select the `optim-plans-executor` subagent with `--agent` as a foreground standalone agent, not `--bg` and not a hidden background subagent. The controller runs items in serial topological order. Each item starts from the latest verified checkpoint commit; dependents do not start until every dependency has a checkpoint.

Worker exit records `worker_completed` only. The controller runs the verification argv, then audits tracked, staged, untracked, ignored, symlink, gitlink/submodule, nested-repository, and out-of-scope deltas. It also checks protected Git metadata: source HEAD/ref, refs except the run branch, config, hooks, and registered worktrees. Only passing controller verification plus path and protected Git metadata audits records `item_verified` and creates the checkpoint commit. Drift is preserved as evidence and is not auto-restored.

Path allowlists are integration allowlists, not host confinement. The trust boundary is repository-integrity detection and integration gating for a trusted local repo/process; it is not host confinement, and it does not prevent a trusted worker from writing outside the worktree or touching shared metadata before detection. Hooks and agent sandboxes are defense in depth.

Failures enter `awaiting_retry_decision` with bounded evidence and without a checkpoint. They do not automatically create retry or finish questions; `request_retry` and `request_finish_approval` are manual recovery commands. The first retry for an item restores without an approval nonce; explicit retry approval for later retries is required. Auto-complete cannot approve finish-wrap integration, cleanup, merge, push, PR, keep, discard, retry restoration after the first retry, waivers, or `not_achievable`; delegated agents cannot approve them either.

After every item is verified and the final audits pass, execution automatically fast-forwards the clean checked-out manifest destination branch to the final checkpoint, runs the full local proof, records `run_finished` with outcome `integrated`, preserves the run worktree and branch, and releases only the matching active pointer. If a precondition or fast-forward check fails before destination mutation, record `awaiting_integration` with bounded evidence and leave the destination unchanged. If full proof fails after fast-forward, record `integration_verification_failed` with stage plus before/after destination OIDs and keep lifecycle `awaiting_integration`; status must create or surface a finish approval with `integrated`, `pr-opened`, `kept`, `discarded`, `failed`, and `aborted`. Manual finish recovery can still record one evidence-backed outcome: `integrated` proves the manifest-bound local destination contains the final checkpoint, requires the checked-out destination worktree to match that object, then runs the full local proof before `run_finished`; proof failure records `integration_verification_failed` and stays in integration recovery, `pr-opened` proves the PR URL and fetched remote ref contain it, `kept` preserves the run worktree and branch, and `discarded` requires explicit confirmation and removes only validated controller-owned state. `Failed` or `aborted` records failure or abort evidence in the terminal event and preserves the worktree unless confirmed discard is requested.
